What this is

Iceberg is a computer that lives in your GitHub account and runs in your browser.

Concretely: a real Alpine Linux system — a kernel, processes, a package manager, a filesystem — emulated by WebAssembly inside the page you have open. Its saved states live in a private repository on your own GitHub account. There is no server of ours between you and it. There is no account with us. If this website disappeared tomorrow, your machines would still be sitting in your repository, and any copy of this static site would open them.

The point is not that Linux can run in a browser; that has been true for years. The point is that a machine can be a thing you save under a name and open somewhere else — the way a document is.

The name is the mental model. What you are looking at — the running session, the terminal, the file you have open — is the freeboard: the small part above the waterline, temporary and exposed. The mass is underneath, in your repository, and it is the part that persists. Nine tenths of an iceberg is below the line, and so is nine tenths of this.

The words

Floe
A saved machine. Immutable, named, complete. Internally a commit; you never have to know that.
Session
A machine you are using right now. Lives in this browser tab and nowhere else.
Drift
Everything the session has changed since it was thawed. The number in the ribbon.
Thaw
Turn a floe into a running session.
Calve
Turn the current session into a new floe.
Melt
Throw the session's drift away and come back up from the floe.
Scuttle
Shut the machine down entirely.
BASE
The factory machine. The first floe, permanent, never editable.
Vault
Your private repository, iceberg-vault.
Keel
The deduplicated store of filesystem pieces inside your vault — the mass below the line that every floe is assembled from.
Awash
Light sleep. The processor is parked but the machine is still in memory.
Submerged
Deep sleep. The machine is written to local storage and the emulator is torn down.
Shelf
Where your floes are listed. The first screen after signing in.

Getting started

  1. Make a key. Iceberg asks for a fine-grained GitHub personal access token scoped to your own account, with three permissions: Administration (read/write, to create the vault once), Contents (read/write, the whole product), Metadata (read, which GitHub adds for you). Nothing else. It is pasted into the page and sent only to api.github.com, only as an Authorization header.
  2. The vault appears. Iceberg creates iceberg-vault as a private repository and lays down its structure. If it already exists, Iceberg adopts it and repairs anything missing. If a public repository of that name exists, Iceberg refuses to use it and says so — a machine is not something to leave in the open.
  3. Name your machine. Username, hostname, password, time zone, shell. Iceberg starts a clean Alpine system, applies them, and calves the result as BASE.
  4. Use it. After the first run it is one tap: open the site, pick a floe, thaw.

Once the vault exists, narrow the key on GitHub to only iceberg-vault. On first use it has to cover your whole account because the repository does not exist yet — that is a GitHub constraint, not a Iceberg preference.

Floes and sessions

This distinction is the entire product, so it is worth being precise about it.

Nothing that happens inside a running machine is ever written to GitHub on its own. No autosave. No background commit. No sync indicator quietly persisting your work. Install four hundred packages, delete the kernel, fill the disk with junk — as far as your vault is concerned, none of it happened.

Work exists in the session until you calve it. That is a deliberate cost: it means you must decide. It buys something worth the price — the floe you thawed from is exactly, permanently, as it was, and experimenting has no consequences you did not choose.

The ribbon always shows how much drift you are carrying, and every route out of the machine — closing the tab, going to the shelf, thawing something else — asks first.

BASE

BASE is the clean install with your identity applied. It is the first floe, and it is special in three ways: it cannot be renamed, it cannot be forgotten, and nothing you do can modify it.

To make a "better BASE", thaw BASE, change what you like, and calve under a new name. BASE stays where it is. This is the only way, and it is deliberate: the value of a factory state is that it is always there, including on the day you have broken everything else.

BASE
 └─ Rust Dev
     ├─ Rust + WASM
     │   └─ Project X
     └─ Rust + LLVM

Calving

Calving is what a glacier does when a new mass breaks off it and floats away under its own name. That is exactly the operation: the session breaks off the floe it came from, becomes independent, and the parent is unchanged.

When you calve, Iceberg walks the machine's filesystem, works out which pieces your vault already holds, and uploads only what is genuinely new. Then, as a single final act, it writes one commit containing the new manifest and the updated index.

The order matters. Until that last commit lands, nothing in your vault refers to any of the uploaded pieces — so a calve interrupted by a dead connection leaves the vault exactly as it was, rather than half-applied. GitHub collects the orphaned pieces on its own schedule.

A calve reports real numbers: pieces uploaded, pieces already held, bytes sent, seconds taken. There is no percentage invented from a timer.

Warm floes

Optionally, a calve can also capture the machine's memory — every running process, your editor still open, the compile still half-done. Thawing a warm floe resumes rather than boots.

The costs, plainly: it adds roughly the machine's RAM (512 MB before compression) to that floe, and it ties the floe to the emulator build that made it. Cold floes boot in seconds and are portable across versions. Warm is for the specific case where you want to walk away mid-thought.

Thawing

Thawing resolves a name to a floe, reads its index, and starts a machine against it. Pieces of filesystem are fetched as the guest touches them, not all at once — a boot reads a few hundred files out of tens of thousands, so it starts long before the whole machine has been downloaded.

The factory image is public and CDN-cached, so most of what a thaw needs is a plain cacheable fetch with no token attached. Only the parts that are yours come out of your private vault.

If you are heading somewhere without a connection, use Download everything now on a floe first. It pulls every piece into local storage so the machine thaws offline.

Sleep and wake

Emulating a processor costs a processor. Iceberg will not spend one while you are reading a file.

RunningYou are doing something. Full speed.
AwashThe run loop is parked, after 45 seconds of quiet. Zero CPU. Memory still held, so waking is instantaneous and the guest never noticed a gap.
SubmergedMemory is written to local storage and the emulator is torn down. Costs nothing at all. Survives a reload, a crash, or a phone deciding to take the tab away. Waking takes a moment.

Anything that needs the machine wakes it: running a command, compiling, opening the terminal. Opening, reading, editing and saving files do not, because the filesystem lives on the browser's side rather than inside a disk image.

The state is always shown, and a sleeping machine is never described as doing work.

The editor

The editor is not a program installed inside Alpine. It is browser-side, reading and writing the machine's filesystem directly. That is why it keeps working with the processor parked, and why opening a file wakes nothing.

It is CodeMirror 6: it works properly on touch, it is a fraction of the payload of the alternatives on a phone connection, and it does not need a worker per language just to open a file.

One honest caveat. A file written by the editor while the machine is asleep may already be in the guest's page cache. Iceberg drops the guest's caches when it wakes after external edits, but if you write a file from the editor and read it in the same instant from a shell that already had it open, trust the shell's copy and re-open.

Files that have drifted since the thaw are marked warm in the file tree, so you can see what a calve would capture without opening a dialog to find out.

On a phone

The phone case is a design target, not a responsive afterthought.

  • A key rail above the keyboard with the characters a shell needs and a phone lacks: Esc, Tab, a sticky Ctrl, pipe, tilde, slash, arrows.
  • A history strip of your recent commands as tappable chips, because retyping a long command on glass is the actual reason people give up.
  • Three panes — files, terminal, editor — one at a time, switched from a bar at the bottom within thumb reach.
  • Keyboard-aware layout using the visual viewport, so the terminal resizes to what is left rather than hiding behind the keyboard.
  • Submerged on hide. Mobile browsers reclaim background tabs aggressively. When the tab goes away, the machine is written to local storage, and it is still there when you come back.

What a phone cannot change: an emulated processor on a phone is slow, and a phone will run its battery down doing it. Editing, scripting, small builds and getting yourself out of trouble are realistic. A full Rust rebuild is not.

Software and networking

This is the part most likely to surprise you, so it is stated up front rather than discovered.

The emulated machine has no internet connection by default. A browser cannot open a raw TCP socket; the guest's network card has nothing to plug into. This is a property of browsers, not a gap in Iceberg.

There are two honest ways to have software:

The courier (no infrastructure)

Iceberg can fetch an Alpine package in the browser and hand the file to the machine, then install it from disk. This works without any server, for any package reachable from a mirror that permits cross-origin reads. Dependencies are resolved from the index the same way.

A network relay (yours)

v86 can attach its network card to a WebSocket relay, which gives the guest real connectivity — apk add, git clone, curl, all of it. Iceberg lets you point at a relay you run or trust. It ships none, and defaults to none, because a relay sees your machine's traffic and that is not a thing to hand a stranger by default.

Either way, once software is installed and calved into a floe, it is in the floe. Thawing it needs no network beyond your vault.

Storage and the keel

A machine is not stored as a disk image. If it were, every floe would cost the whole machine again, and a vault with a dozen environments would be tens of gigabytes.

Instead, the filesystem is treated as one long byte stream — every file's contents, in path order — and cut into pieces at boundaries chosen by the content rather than by position. Each piece is stored once, under its own hash. A floe is a list of hashes plus an index that says which file lives where.

The consequence: two floes that share a compiler share its pieces exactly. Adding a compiler to a saved machine costs the compiler, not the machine.

Content-defined boundaries are what make this hold up. Insert a file near the front of the stream and every byte after it shifts; fixed-size blocks would then differ all the way down. Content-defined boundaries re-synchronise within about one piece.

What this means for you

  • Your first calve after installing a toolchain is the expensive one. Subsequent calves of the same machine are usually a few megabytes.
  • The factory image is not copied into your vault. It is public, immutable, CDN-served, and pinned by hash. Your vault holds what you made, plus a reference.
  • Forgetting a floe removes it from the shelf. Its pieces stay in the repository until GitHub next collects what nothing references. Iceberg cannot force that and does not claim to.
  • Iceberg warns above 800 MB and refuses to calve above 2 GB. GitHub's own guidance is to stay under 1 GB per repository.

Several devices

Floes sync because they are in a Git repository; there is nothing else to sync. Calve on the laptop, thaw on the phone.

Sessions do not sync, and cannot: a session is a running processor in one browser tab. Two tabs are two machines.

If another device calved something while you were working, Iceberg notices before it writes — the vault's ref update is a compare-and-swap, so a lost race is reported rather than resolved by overwriting. Both floes land; a name collision is refused with the reason, and nothing you did is lost.

Never is a saved floe overwritten silently.

Security and privacy

What Iceberg can reach

The key you make is fine-grained and, after first use, scoped to one repository. Iceberg cannot read your other repositories, cannot touch secrets, cannot run Actions, cannot open pull requests. The permission table is shown before you create the key, and the list of things deliberately not requested is shown next to it.

Where the key lives

In sessionStorage, which dies with the tab. "Remember on this device" wraps it with AES-GCM under a key derived from your passphrase (PBKDF2, 310 000 rounds); the raw token never touches persistent storage. It is sent only to api.github.com, only as a header — the API client asserts the target origin before every single request and throws otherwise.

The guest never gets your credentials

This one is structural. The emulated machine loads filesystem pieces through a virtual origin that does not exist on the internet: requests to it never reach the network and are answered by Iceberg, on this side of the boundary. The guest cannot see the handler, cannot reach past it, and never possesses a GitHub token. Software you install inside the machine cannot use your GitHub access, because it does not have any.

What is not protected

  • The machine is not a sandbox from you. It is your computer running your software in your tab. v86 is an emulator, and its own security model is that of ordinary browser JavaScript — code in the guest is confined to the emulator, but the emulator is not a hardened boundary and has never claimed to be. Do not run something you would not run on your laptop.
  • Your vault is private, not encrypted. Anything you put in a floe — passwords in dotfiles, SSH keys, tokens — sits in a private GitHub repository in the clear, readable by anyone with access to your GitHub account. Treat it exactly as you would treat a private repo, which is to say: do not put secrets in it.
  • Local storage is not private on a shared computer. Submerged images and cached pieces sit in the browser's storage for that origin. Sign out clears the key; it does not scrub the cache. On a machine that is not yours, use a private window and scuttle when you are done.

Limits, honestly

SpeedAn emulated x86 in WebAssembly runs perhaps 10–30× slower than the host, single core. Real for editing, scripting, small builds. Not a build farm.
MemoryThe guest gets 512 MB by default; the browser tab holds that plus the filesystem. A tab over roughly 2 GB is at risk on any device, and on iOS considerably less.
Architecture32-bit x86. Software with no x86 Alpine package will not run.
NetworkingNone in the guest without a relay you supply. See Software and networking.
GitHub API5 000 requests an hour. A first calve of a large toolchain can use several hundred. Iceberg tracks the budget, slows down as it thins, and refuses to start something it cannot finish rather than dying halfway.
Repository sizeGitHub is comfortable to about 1 GB and pushes back well before 5 GB. Iceberg warns at 800 MB.
Single filesFiles over 48 MB inside the machine are refused at calve time, by name, rather than silently dropped.
Local storageBrowsers evict. Iceberg asks for persistent storage and tells you if the browser declines. An uncalved session is only as safe as the browser feels like being.
Background tabsAre throttled and eventually discarded, especially on mobile. Submerged exists for exactly this.
Warm floesTied to the emulator build that made them. If the emulator is upgraded, warm resume may be refused; cold floes are unaffected.

When something breaks

The calve failed halfway
Nothing was applied. Uploaded pieces are orphans and GitHub collects them; your shelf is untouched. Try again — the second attempt is faster, because the pieces that did upload are already there.
"A piece of this floe is missing"
The index refers to something the vault does not hold, which means a calve did not finish and its commit landed anyway (very rare, or the result of hand-editing). Other floes are unaffected. Forget the damaged one.
The shelf is empty but the vault has floes
The index file is damaged. The manifests are the record; the index is a convenience. Rebuilding regenerates it from them.
GitHub says the key is missing a permission
The message names the exact permission from GitHub's own response header. The one people forget is Administration, needed once to create the vault.
The machine will not start
Almost always the emulator failing to load its WebAssembly — an extension blocking it, or a hosting setup serving the wrong content type. The console will say. On file:// nothing works at all, because Web Crypto is withheld outside a secure context.
The tab was killed with uncalved work
Check the shelf on reload: if submerged was reached, the whole machine comes back. Failing that, Iceberg spills changed small files to local storage every minute, which is a way to recover a file, not a backup of the machine.

Architecture

For the technically curious. The full document, including the parts that are genuinely impossible from a static site and what is done instead, is ARCHITECTURE.md in the source repository.

  your browser                          github
  ────────────                          ──────
  v86  ── 9p filesystem ──┐
   │                      │
  xterm / CodeMirror      │   virtual origin (no network)
   │                      ▼
  session  ──drift──▶  snapshot ──cut──▶ keel ──blobs──▶ iceberg-vault
                                                              (private)
                          ▲
  factory image ──────────┘  public, CDN, pinned by hash
  • Two repositories. The site is static and public. Each user's machine lives in their own private repository. There is no shared database, and nothing of yours passes through anything of ours.
  • One commit per calve. Chunks are uploaded as blobs first; a single commit then introduces the manifest and the index together, so a partial upload is invisible.
  • Compare-and-swap refs. Two devices calving at once produce two commits, never a lost one.
  • Content-defined chunking. A Gear rolling hash with a 1 MB average, 256 KB floor, 4 MB ceiling, over a path-ordered byte stream.
  • Lazy filesystem loading. The emulator asks for a file by content hash; Iceberg answers from the keel. A boot fetches what a boot reads.
  • One optional relay. "Sign in with GitHub" needs a stateless shim because GitHub's token endpoints send no CORS headers and require a client secret. It is about fifty lines, stores nothing, and deployments may simply not run it — the key path needs no infrastructure at all.

Questions

Is this a VM in the cloud?
No. There is no machine anywhere but your browser. Close the tab and the computation stops.
Can I run Docker in it?
No. 32-bit x86, no nested virtualisation, no network by default.
Does it work offline?
A thawed machine keeps running with no connection. Calving needs GitHub. Download a floe in advance to thaw it offline.
Will my code end up on your servers?
We have no servers. The site is a static page; the only thing it talks to is GitHub, with your key.
What happens if you shut this down?
Your vault is a normal Git repository you own. Any copy of this static site opens it, including one you host yourself. The formats are documented so a third tool could read it too.
Why not just use a devcontainer?
If you have a machine that can run one, do. Iceberg is for the times you do not, and for keeping the machine itself rather than a recipe that rebuilds something like it.
Can I make BASE different?
Not in place, deliberately. Thaw it, change it, calve under a new name, and thaw that from then on.
Is it a sandbox?
No.
